Plak de tekst onder de streep in je geplande taak voor Run A, ter vervanging van de
huidige lange prompt. Hij is kort met opzet: de inhoudelijke regels staan in de repo, dus je
kunt ze aanpassen zonder de scheduler nog aan te raken.

Doe hetzelfde voor de andere run met het bijbehorende SCHEDULER-bestand. Beide taken wijzen
naar DEZELFDE branch; dat is bewust, run: "A"/"B" in het schema houdt ze uit elkaar. Plan ze
niet op hetzelfde tijdstip.

DE WERKBRANCH IS: main — en die naam verandert nooit meer.

Dat is met opzet een vaste naam en geen sessienaam. Claude Code geeft elke sessie een eigen
willekeurige branchnaam, dus een sessienaam in deze tekst loopt gegarandeerd uit de pas. Dat
is drie keer misgegaan:

   9 aug 2026  — de scheduler wees naar claude/zealous-keller-ja4wwn terwijl het werk zeven
                 commits verder stond op een andere tak.
  10 aug 2026  — Run A startte op de tak van Run B, miste twee regels die Run A zelf de dag
                 ervoor had toegevoegd, en publiceerde een bet die onder de volledige
                 regelset niet had gemogen.
  10 aug 2026  — Run A en Run B legden allebei hun run op een eigen tak vast; beide ledgers
                 waren onvolledig en Run B trok op halve data de verkeerde conclusie over de
                 kwaliteit van het eigen model.

Twee maatregelen samen zetten dat dicht: stap 0 hieronder voegt bestaande takken samen, en
stap 6 pusht naar main zodat er geen nieuwe bijkomen. "Pak de nieuwste branch" is expliciet
NIET genoeg — op 10 aug bevatten beide takken werk dat de ander niet had, dus kiezen betekende
hoe dan ook iets weggooien. Samenvoegen is de opdracht.

Zet main ook als default branch in de GitHub-instellingen.

CONTEXT: Dit is een door de gebruiker zelf aangemaakte, terugkerende geplande taak. De
gebruiker heeft deze opdracht vooraf goedgekeurd. Voer 'm zonder verdere bevestiging uit;
er is geen live gebruiker om iets aan te vragen.

Werk in de repo /home/user/football. De canonieke branch is main, en je hebt hierbij
expliciet toestemming om daarheen te pushen — ook als deze sessie op een andere branch is
gezet. Zonder die toestemming weigert een sessie dat.

0. EERST DE BRANCHES OP ORDE. Doe dit vóór alle andere stappen.
   a. `git fetch origin` en `git branch -r` — bekijk ALLE branches, niet alleen main.
   b. Bepaal per branch of hij commits bevat die jij nog niet hebt:
      `git rev-list --count HEAD..origin/<andere>`. Is dat 0, dan kun je hem negeren.
   c. Bevat een andere branch wél eigen commits, merge hem dan. Kies niet tussen takken en
      gooi er geen weg: op 10 aug 2026 hadden beide takken werk dat de ander niet had. Bij
      conflicten in data/picks.jsonl, data/source-health.json en data/coverage.json is de
      VERENIGING het antwoord — beide runs hebben echt gemeten, en een pick die op één tak
      staat is een echte pick. Bij _shared-rules.md en de scripts wint de nieuwste versie.
   d. Controleer daarna of picks.jsonl openstaande picks bevat van een run die op de andere
      tak nooit is afgewikkeld. Die horen bij Stage 0.
   e. Kom je om wat voor reden dan ook niet op main uit, meld dat dan bovenaan het runrapport
      én in de notificatie.

1. Lees prompts/run-a.md en prompts/_shared-rules.md. Die twee bestanden zijn de opdracht —
   volg ze onverkort, inclusief de parameters, de 0-of-1-bet-regel, de vijf poorten in §1
   (waaronder de bevestiging door een tweede methode), de anti-circulariteitsregel, de
   pipeline Stage 0 t/m 6 en het outputformat. Lees ze ná stap 0, niet ervoor: vóór de merge
   kun je een oudere versie van de regels in handen hebben.
2. Draai eerst `python3 scripts/api_check.py` en lees dan data/source-health.json en
   data/coverage.json, zodat je niet opnieuw tijd verliest aan bronnen die vorige run al
   faalden. Neem de uitvoer van api_check.py over in het runrapport. Wordt een sleutel
   afgewezen of ontbreekt hij, meld dat expliciet — niet stilzwijgend doorgaan.
3. Voer de run uit voor de wedstrijden van VANDAAG (bepaal zelf de actuele datum).
4. Leg de run vast volgens _shared-rules.md §6: runrapport, picks.jsonl, source-health.json,
   afwikkeling van openstaande picks, en commit + `git push origin HEAD:main` (zie §6a). Maak
   ook het leesbare dagrapport van §6c (prose.json + scripts/report.py) en publiceer het als
   Artifact — ook bij nul bets.
5. Stuur een notificatie volgens _shared-rules.md §7, met de link naar dat dagrapport erin.

Nul bets is een geldige uitkomst. Forceer geen picks om het format te vullen.
